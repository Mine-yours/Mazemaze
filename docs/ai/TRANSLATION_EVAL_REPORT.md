- 位置づけ: Mazemaze のモデル選定と、今後の改善検証の**基準資料**。モデルの最終選定ではない（§10）。

## 0. 要約

- 30文章・63スパンを、2つのローカルモデルで翻訳し、Claude Opus 5.5 がモデル名を伏せた A/B 比較で採点した。表示順を入れ替えた60入力すべてが有効（正常60、不正0、欠落0）。
- 機械検証の不採用率は両モデルとも **3.2%**（各 2/63）。
- 両モデルとも採用された60スパンの対応あり比較で、加重平均は **Qwen 3.99、TranslateGemma 3.43（差 +0.56）**。Judge の優劣判定（両順序一致のみ）は Qwen の勝ち37、TranslateGemma の勝ち6、同点8、不一致9。A/B 反転の判定一致率は **85.0%**（51/60）。
- 差が最も大きいのは**文脈適合性**（+0.93）で、Judge は句読点の重複・文中の大文字・末尾の `...` といった**表示上の崩れ**を強く減点している。TranslateGemma は採用された訳の95%が文末句読点で終わり、95%が大文字で始まる（Qwen は 34% と 57%）。差の一部は、翻訳内容ではなく出力形式に起因する。
- 固有名詞を含む文章では、主として文脈適合性や自然さの違いによって Qwen が高く評価された。一方、固有名詞の翻訳精度自体は両モデルで大きな差が確認されていない。𠮷野家や𠮷田さんなどの Unicode を含む固有名詞では、両モデルに誤訳が見られた（§5）。
- 重大な誤訳は両モデルに残る（Qwen 10スパン、TranslateGemma 9スパン）。Qwen はスパン外の語を取り込む誤り（addition）が多く、TranslateGemma は文脈を受け取らないことに由来する誤りが見られる。
- 暫定判断: **Qwen3.5:9b を初期モデルの第一候補とする**。ただし、表示上の問題と翻訳内容の問題を切り分ける検証と、人手確認を経てから判断する（§10、§11）。

## 1. 目的・対象・規模

### 1.1 目的
Mazemaze は、日本語の文章の一部を英語に置き換えて学習させるアプリである。そのため、全文翻訳としての流暢さだけでなく、次の性質を重視して比較した。

1. 指定したスパン以外の日本語を変えないこと（原文保持。`CLAUDE.md` §5）。
2. 指定スパンの意味を正しく英語にすること。
3. 英語を埋め込んだ後の混在文として、重複・破綻なく読めること。
4. 固有名詞・URL・数値などを誤って改変しないこと。
5. 検証に失敗した置換は日本語のまま残し、全文を壊さないこと。

### 1.2 対象モデルと実行条件
実行は Ollama 0.33.3、`127.0.0.1` のローカルのみ（`run_meta.json`）。

| 項目 | Qwen3.5:9b | TranslateGemma:12b |
|---|---|---|
| 量子化 | Q4_K_M | Q4_K_M |
| 呼び出し単位 | 1項目につき1回（全スパンを JSON Schema 出力） | スパンごとに1回（公式の翻訳プロンプト形式） |
| 文脈の与え方 | 全文を文脈として渡す（`full_text`） | 文脈欄なし。スパン単独で翻訳（`none`） |
| temperature / seed | 0 / 42 | 0 / 42 |
| num_ctx / num_predict | 4096 / 512 | 2048 / 256 |
| think | false | （該当なし） |

**比較条件は完全には揃っていない**（特に文脈の与え方）。判断の根拠は `docs/ai/DECISIONS.md`「モデル別 Adapter を分ける」。

## 2. 評価方法

### 2.1 Judge
- Claude Code のサブエージェント `translation-judge`（`model: opus`）を使用。新しい API キーは使わない。実行メタデータで、評価に応答した全件が `claude-opus-5-5` であることを確認した（自己申告も60/60が同じ値）。
- Judge に渡したのは許可リストの項目（評価項目 ID、日本語原文とスパン、A/B の候補訳・混在文・採否）だけ。モデル名・対応表・パス・Git 情報・秘密情報は渡していない（`prepare` の漏えい走査で検証）。
- 評価データの範囲はリポジトリのテストデータとその生成結果のみ。一般ユーザーの文章は評価していない。
- Judge の `PreToolUse` フック（`Read|Grep|Glob` を拒否）の効果は 2026-10-08 に実測した（`eval/judge/README.md`「フックの実測確認」）。これは OS レベルの隔離ではない。

### 2.2 評価軸と重み

| 評価軸 | 重み | 内容 |
|---|---:|---|
| 意味の正確性（accuracy） | 40% | 原スパンの意味が保たれ、重要な追加・欠落がない |
| 英語の自然さ（naturalness） | 25% | 自然な英語で、敬語などの丁寧さが適切 |
| 文脈適合性（context） | 25% | 原文全体・混在文の他の部分と整合し、重複・矛盾しない |
| 固有名詞・数値（proper_nouns） | 10% | 名前・数値・URL 等が正しく保持される。該当しなければ null |

- 1〜5点。該当しない軸（null）は除外し、残りの重みを再計算する。全軸 null は「評価不能」で、0点にしない。
- 正確性と自然さは必須（null 不可）。
- 重大な誤訳（`mistranslation`）・追加（`addition`）・欠落（`omission`）・固有名詞の誤り（`proper_noun`）は個別に記録し、正確性は2以下とする指示。
- **この重み（40/25/25/10）自体は検証されていない**（§9）。

### 2.3 匿名 A/B 比較
- 候補はモデル名を伏せた A/B で渡す。同じ項目を A→B と B→A の2順序で、別々の呼び出しで評価する（各項目2入力）。
- 2順序の判定が一致した場合のみ優劣を採用する。片方が tie でもう片方が勝敗なら「不一致」。
- モデル名と A/B の対応は run の `blind_key.json`（ローカル）にだけある。

### 2.4 機械検証と不採用の扱い
- 翻訳結果は、アプリ側の検証（形式・日本語混入・長さ・前置き・プレースホルダ・URL／メール／数値の欠落・スパン外の混入など）を通ったものだけを採用する。
- 検証で不採用のスパンは、日本語のまま残る。Judge には `status: rejected`、`english: null` と、表示される混在文だけを渡す。**不採用候補には点数を付けず**、`rejected_by_validator` として別集計する（今回、不採用候補に点数が付いた記録は0件）。

### 2.5 集計の定義
- **採用済み平均**（§4.2）: 各モデルの、検証を通り、有効な採点があったスパンの平均。モデルごとに母集団が異なる。**生存バイアス**があり、不採用の多いモデルが有利に見えうる。
- **対応あり比較**（§4.3）: 両モデルとも採用された60スパンを単位とする。A/B 反転の2順序は**独立したスパンとして数えず**、スパンごとに有効な順序の加重平均を取ってから、モデル間の差（Qwen − TranslateGemma）を求める。信頼区間は、スパンの差を10,000回復元抽出するブートストラップ（seed 42）。符号検定は同点を除いた片側の多寡の参考値。
- **A/B 一致率**（§4.4）: 両候補が採用され、2順序とも判定できたスパンのうち、判定が一致（同じモデルの勝ち、または両順序で tie）した割合。

## 3. 評価の実施経緯

評価は次の経緯で完了した。再現と監査のために記録する。

1. **試験評価と再利用**: 先に5項目・10入力で試験評価を行った。本評価の最初の10入力（keigo-01、unicode-01、injection-01、keigo-02、keigo-03）は、この試験評価の応答を `judge_full30/raw/` に複製して**再利用**した（入力の `input_id` と JSON 本文が完全一致することと、コピー前後のハッシュ一致を確認。コピー元は変更していない）。新たに送信したのは残り50入力だけ。
2. **unicode-03 の初回送信が不合格**: このデータは Unicode 正規化の検証用に、`か`＋`U+3099`、`e`＋`U+0301` の分解形をあえて含む。初回送信では、私のプロンプトへの書き写し時に合成形へ変わり、Judge が準備済みの入力と違う文字列を受け取った。照合で不一致を検出し、**保存せず**、有効な結果として採用しなかった。
3. **unicode-03 の再送**: 準備済みの JSON から、プログラムで ASCII エスケープ形式（`json.dumps(..., ensure_ascii=True)`）の送信用テキストを生成し、復元後の全フィールド・コードポイントが一致することを送信前に確認した。実際には、ツール呼び出しの層でエスケープが文字に復元され、Judge には**結合文字 `U+3099`・`U+0301` が保持された状態の原文**が届いた（Judge が受け取った JSON を復元して準備済み JSON と完全一致を検証済み。エスケープ表記は Judge には届いていない）。Judge の応答に、エスケープや結合文字を誤解した形跡はなかった（「がんたん」を「かんたんの誤記」と読んだ。これは意図した誤記）。
4. **url-03 の order2 が初回で不正**: Judge が、両候補とも不採用の `s2` を省いて `s1` と `s3` だけを返し、スパン構成の不一致（`span_mismatch`）で不正となった。補完せず、同じ入力を再送した。
5. **再送時の補足指示**: 再送には補足指示を加えた。unicode-03 には Unicode エスケープの解釈についての注意書き、url-03 には全 `span_id`（両候補が不採用のスパンを含む）を出力する旨の出力形式の指示。**採点基準は変更していない**。
6. **旧不正応答の保全**: url-03 order2 の初回の不正応答は、ハッシュ検証済みの複製として `judge_full30/raw_audit/` に保存してある。`raw/` には有効な応答だけがある。
7. **結果**: 最終的に、60入力すべてが有効（正常60、不正0、欠落0）。再送は上記3入力に各1回だけ。

- カテゴリ別のスパン数は、対応あり比較から不採用のスパンを除いた数。unicode は8スパンから unicode-01/s2（TranslateGemma が不採用）を除いた7、url_email_number は8スパンから url-01/s3（Qwen が不採用）と url-03/s2（両モデルが不採用）を除いた6である。

カテゴリ別の傾向（Judge の指摘にもとづく）:

- **敬語**: 「おっしゃった」→「said」、「存じます」→「believe」のように、敬意・謙譲のニュアンスが平板化する傾向が、両モデルの訳に共通して指摘された。
- **口語**: Qwen がスパン外の語（`Hey`、`yesterday`、`Wow`、`But`）を訳に取り込み、混在文で重複した（addition 4スパン）。「寝過ごす」→`fell asleep` は両モデルとも誤訳（降りる駅を過ぎて寝てしまった、という意味が落ちる）。
- **慣用句**: 「口が軽い」→`talkative` は両モデルとも誤訳と指摘された。「火花が散る」→`fly off the handle`（Qwen）は意味が違う。「耳を疑う」→`doubt my ears`（Qwen）は直訳気味で、`couldn't believe my ears` のほうが自然とされた。
- **複文**: TranslateGemma は、スパン単独で翻訳するため、主語を取り違える例があった（complex-01/s3 で「彼」が `I` になった）。
- **URL・メール・数値**: 採用された訳では、URL・メールアドレス・予約番号の欠落・改変は確認されなかった。ただし、Qwen がスパン外の意味を先取りした例（url-03/s1 `can be obtained via`）と、TranslateGemma が宛先を誤った例（url-01/s3 `Please contact me.`）がある。url-03 の s1・s3 では TranslateGemma が高く評価された。
- **Unicode**: unicode-01 は両モデルとも誤訳（§5、§6）。unicode-03（結合文字を含む）は正常に評価できた。

## 5. 固有名詞・数値の扱い

固有名詞を含む文章では、主として文脈適合性や自然さの違いによって Qwen が高く評価された。一方、固有名詞の翻訳精度自体は両モデルで大きな差が確認されていない。𠮷野家や𠮷田さんなどの Unicode を含む固有名詞では、両モデルに誤訳が見られた。

Qwen が固有名詞の処理能力自体で優れている、とは結論づけられない。

### 5.1 2つの数値の定義の違い

固有名詞・数値の軸には、集計方法が異なる2つの数値がある。混同しないこと。

| 数値 | 定義 | 結果 |
|---|---|---|
| 採用済み平均（§4.2） | 各モデルが**自分の**採点を持つスパンの平均。母集団がモデルごとに異なる | Qwen **4.40**（15スパン）、TranslateGemma **4.36**（14スパン） |
| 対応あり比較（§4.3） | 両モデルが固有名詞・数値の採点を持つ**共通の14スパン**で、スパンごとの差を平均 | Qwen − TranslateGemma = **+0.29**（共通14スパンの平均は Qwen 4.64、TranslateGemma 4.36） |

- 母集団が違う理由: Qwen の15スパンには、TranslateGemma が不採用だった unicode-01/s2 が含まれる。Qwen のこのスパン（「Mr. Sada」）の採点は1で、これが Qwen の採用済み平均（4.40）を押し下げている。
- 共通14スパンのうち、2モデルのスコアが同じなのは9スパン。+0.29 は、差のある5スパン（proper-01/s1 が +0.5、unicode-04/s1 が +1、unicode-04/s2 が +0.5、url-01/s1 が +1、url-03/s3 が +1）に由来する。14スパンの小さな標本で、検定していない。
- 固有名詞・数値の軸の差（+0.29）は、他の軸の差（+0.37〜+0.93）より小さい。

### 5.2 カテゴリ「proper_noun」の差は、固有名詞の軸の差ではない

proper_noun カテゴリ（proper-01〜03、6スパン）の平均は Qwen 4.43、TranslateGemma 3.33（差 +1.10）で、Judge の優劣判定も Qwen の6勝0敗だった。これは**加重平均（4軸の合計）の差**であり、固有名詞・数値の軸だけの差ではない。このカテゴリでの固有名詞・数値の軸のスコアは、6スパンすべてで両モデルとも4.5〜5で、人名・地名・社名そのものは両モデルとも正しいと評価された。差の主因は、TranslateGemma の `Yamada Taro is...`（省略記号）や、文頭の大文字・文末のピリオドによる混在文の崩れなど、文脈適合性と自然さである。

### 5.3 固有名詞の誤訳

誤りは unicode のカテゴリに集中した。

- 「𠮷野家」→ Qwen `Sano house`、TranslateGemma `traditional Japanese farmhouse`（両モデルとも誤り）
- 「𠮷田さん」→ Qwen `Mr. Sada`（TranslateGemma は当該スパンが不採用）

人名・店名の誤りは、学習者が誤った表現を覚えるおそれがあるため、優先的な確認対象とする。

## 7. 混在文特有の表示上の問題

今回の評価で重要だったのは、**翻訳内容の誤りと、英訳を日本語に埋め込んだときの表示の崩れが混在している**ことである。

採用された訳の表面的な特徴（各モデル61スパン）:

| 指標 | Qwen | TranslateGemma |
|---|---:|---:|
| 文末句読点（`.` `!` `?` `…`）で終わる | 21（34%） | 58（95%） |
| 大文字で始まる | 35（57%） | 58（95%） |
| 末尾が `...` | 0 | 8 |

- 元の日本語の読点・句点と重複して、`.、` `.。` `.！` のような表示になる例が多い。文中に大文字で始まる英語が入る、末尾に `...` が付いて不自然になる例もある。
- Judge のコメントでは、これらが主に**文脈適合性**の減点理由として挙げられている。文脈適合性の差（+0.93）が他の軸より大きいことと整合するが、因果関係は未検証である。
- したがって、+0.56 の差の一部は、モデル固有の意味理解ではなく、**各モデルの出力形式と、スパンを日本語に組み込む処理との相性**による可能性がある。
- 一方、固有名詞（𠮷野家など）や慣用句、スパン外の語の取り込みのような**内容の誤訳**は、句読点の処理では改善できない。
- 上記の特徴は、表面的な指標であり、Judge の減点との因果関係は、整形前後の比較で確認する必要がある（§11）。

## 9. 限界

- **規模と代表性**: 30文章・63スパンで、カテゴリごとのスパン数は6〜9と少ない。実利用の文章を十分に代表しない。
- **敵対的・難問のデータ**: injection や unicode には、意図的な難問・敵対的なテストが含まれる。通常の利用文での性能を示すものではない。
- **評価軸の重み**: 40/25/25/10 の重み自体は検証されていない。重みの設定次第で結論の強さが変わりうる。
- **文脈評価の混入**: 文脈適合性の点数には、翻訳精度だけでなく、句読点の重複・文中の大文字・省略記号といった**表示上の問題への減点**が含まれる（§7）。
- **Judge は人間の検証の代わりにならない**: 採点は LLM の判断で、正解ではない。同一の Judge（Opus）が両モデルを採点しており、言い回しの好みによる偏りがありうる。**人手採点は未実施**（`human_scores.csv` の `naturalness`・`context_fit` 列は126行すべて空欄）。`review_queue.csv` の22行は人が確認する対象。
- **Judge の再現性**: A/B 反転の2回は独立なサンプルではない。同じ訳でも、順序によって点が動く（同じ候補の2順序間の点差は平均0.24、最大1.17。最大は colloquial-03/s1 の Qwen）。1回の評価では、再現性は完全ではない。
- **比較条件の不一致**: Qwen は全文を文脈として受け取り、TranslateGemma は受け取らない。プロンプト・num_ctx・num_predict も異なる（§1.2）。差には、モデルの能力だけでなく、実行条件の差が含まれる。
- **生成の再現性**: temperature 0・seed 固定でも、出力の完全な再現は保証されない。各モデル1回の実行（repeat 1）。
- **統計**: p値・信頼区間は、同一 Judge の採点に対する記述的な参考値。
- **不採用スパン**: 不採用（各2）は品質平均に含めていない。不採用率と併せて解釈する。
- **処理速度**: 処理速度の比較は、このレポートの採点結果からは確定しない。参考として、元の run の `report.md` では応答時間の median が Qwen 4481 ms、TranslateGemma 4471 ms、p90 が Qwen 5445 ms、TranslateGemma 6132 ms（各30件・1回）。ただし、呼び出し単位が異なる（Qwen は項目ごとに1回、TranslateGemma はスパンごとに1回。§1.2）うえ、元の集計方法は本レポートでは再確認していない。繰り返し計測を含む別の検証が必要。
- **データの扱い**: 評価データは Claude Code の会話履歴に残る（`eval/judge/README.md`）。対象はリポジトリのテストデータだけ。

## 10. 暫定判断: Qwen3.5:9b を初期モデルの第一候補とする理由

**第一候補とするが、最終選定ではない。**

理由:

1. 対応あり60スパンで、加重平均が +0.56（95%区間 +0.37〜+0.75）、スパンごとに Qwen が高いのが38、TranslateGemma が13。Judge の優劣判定も Qwen 37勝、TranslateGemma 6勝で、方向が一貫している。
2. 差は**文脈適合性だけでなく、正確性（+0.37）、自然さ（+0.56）、固有名詞・数値（+0.29）の各軸にも**ある。Qwen が低い軸はない（ただし、自然さにも表示上の問題への減点が含まれうる）。
3. 機械検証の不採用率は同じ（3.2%）で、この点では差がない。
4. Qwen は全文を文脈として受け取れる（TranslateGemma は受け取れない）。この実行条件の差が結果に寄与している可能性があり、同条件での比較は未実施（§11）。

留意点（第一候補を覆しうる条件）:

- 重大な誤訳は Qwen 10スパン、TranslateGemma 9スパンで、**Qwen に誤訳リスクがないわけではない**。特に、スパン外の語を取り込む誤り（addition）は Qwen に多い。
- 差の一部は表示上の問題に由来する可能性があり、**句読点などを整形した後の比較**で差が縮む可能性がある。
- 人手採点が未実施で、Judge 以外の裏付けがない。
- 処理速度は未確定（§9）。
- 比較条件が揃っていない（文脈の与え方）。

最終選定は、§11 の検証と人手確認の後に判断する。

## 11. 次の開発・改善の優先順位

優先度順。ここでは方針のみで、実装は別途の指示を待つ。

1. **人手確認（最優先・低コスト）**: `review_queue.csv` の22行（重大誤訳の指摘19、A/B 不一致9。重複あり）を人が確認する。Judge の指摘が妥当かを検証し、`human_scores.csv` による人手採点も進める。Judge の限界（§9）への最も直接的な対策になる。
2. **表示上の問題と翻訳内容の誤りの切り分け**: 既存の翻訳結果は変えず、訳文の先頭・末尾の整形（文末ピリオド・文頭の大文字・末尾の `...`）だけを適用した場合の混在文を作り、整形前後の差を比較する。Judge による再評価が必要で、元の run は変更せず、新しい run として扱う。整形で差がどれだけ縮むかが、モデル間の差の本質を示す。
3. **句読点処理の設計**: 日本語の原文は変更せず、英訳スパンの先頭・末尾だけを必要に応じて整える仕組みを検討する。ピリオドの一括削除は行わない。略語、小数、引用符、感嘆符、疑問符、三点リーダーに影響しうるため、実例とテストで安全性を確認する。
4. **重大な誤訳への対策**: 固有名詞（Unicode の異体字を含む）、慣用句、口語、スパン外の語の取り込み（addition）を優先して分析する。必要に応じて翻訳プロンプトや検証ロジックの改善を検討するが、評価の再現性のため、既存の run は変更しない。
5. **比較条件の確認**: TranslateGemma に文脈を与えられるか、Qwen の文脈を外した場合に結果がどう変わるかなど、実行条件の差を切り分ける検証を検討する。
6. **処理速度の確認**: 繰り返し計測で、呼び出し単位の違いを考慮した比較を行う。
7. **アプリへの組み込み**: モデルの暫定選定後に、FastAPI とスマートフォン対応の Web 画面を実装する（`CLAUDE.md` に従い、変換失敗時は原文を表示する安全なフォールバックを維持し、ローカル実行を基本とする）。
